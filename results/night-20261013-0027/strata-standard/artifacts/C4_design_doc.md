# ローカルLLMの夜間ベンチマーク 設計書

- 文書バージョン: 1.0.0
- 最終更新日: 2025-01-15
- 状態: 草案(レビュー待ち)

---

## 目的

### 背景

当チームでは、開発支援・要約・コード生成などの用途でローカルLLM(以下「ローカルLLM」)の導入を進めている。日中は開発者がモデルを対話的に利用するため、性能測定を日中に実施すると、他の作業とリソースを競合し、正確な測定値を得られない。また、GPUメモリや電力消費の観点から、日中の測定は開発環境の安定性を損なうリスクがある。

そこで、開発者の活動が少ない夜間時間帯(22:00〜翌朝7:00)に自動でベンチマークを実行し、モデルの性能・安定性・リソース使用状況を継続的に計測する仕組みを設計する。

### 達成したいこと

1. **性能の定量化**: 推論速度(トークン生成速度)、初動遅延、メモリ使用量などの主要指標を統一条件で計測し、時系列で蓄積する。
2. **回帰の早期検出**: モデル更新、推論エンジン(例: llama.cpp, vLLM, Ollama)のバージョンアップ、ドライバ更新などが性能に与えた影響を、閾値超過の検知により早期に発見する。
3. **比較評価の再現性確保**: 同一ハードウェア・同一プロンプトセット・同一パラメータで反復実行し、モデル間・バージョン間の公平な比較を可能にする。
4. **運用コストの可視化**: 電力消費と実行時間に起因する運用コストを推定し、導入モデル選定の判断材料を提供する。
5. **無人運用**: 人の介入を要さず、スケジューラによる自動実行、自動レポート生成、異常時の自動通知までを一気通貫で実現する。

### 対象外(スコープ外)

- 学術的な品質評価(例: MMLU, HumanEval などの公開ベンチマークでの順位争い)は本設計の主目的としない。品質評価は補助指標として扱う。
- クラウドAPIサービス(Azure OpenAI, Anthropic API など)との比較は本フェーズでは行わない(将来の拡張候補)。
- 分散GPUクラスタでの推論は対象外とし、単一ワークステーション(単一ノード)のみを対象とする。

## 構成

### 全体アーキテクチャ

夜間ベンチマークシステムは、以下の5つの要素で構成する。

1. **スケジューラ**: cron / systemd timer により夜間時間帯にジョブを開始する。
2. **ランナー(実行オーケストレータ)**: Python製のスクリプト `bench_runner.py` が、対象モデルとタスクを直列に実行し、結果を構造化して収集する。
3. **推論エンジン層**: llama.cpp / vLLM / Ollama のいずれかをモデルごとに起動し、統一インターフェース(OpenAI互換HTTP API)経由で呼び出す。
4. **計測・収集層**: 推論メトリクス(生成速度、初動遅延、メモリ)とシステムメトリクス(GPU使用率、温度、電力)を収集し、JSON Lines形式で保存する。
5. **レポート・通知層**: 結果をSQLiteに格納し、Jinja2テンプレートでHTML/Markdownレポートを生成、Slack/Webhookへ通知する。

### 実行フローの階層

```
[cron 22:00]
   └─ bench_runner.py (オーケストレーション)
        ├─ プリフライトチェック (GPU状態, ディスク空き, 既存プロセス検知)
        ├─ モデルループ (対象モデルごとに以下を実行)
        │    ├─ 推論エンジン起動 (サブプロセス)
        │    ├─ タスクループ (タスクごとに以下を実行)
        │    │    ├─ プリフィクスプリフィル測定
        │    │    ├─ デコード速度測定
        │    │    └─ 出力品質チェック (ハッシュ/簡易スコア)
        │    └─ 推論エンジン停止・クリーンアップ
        ├─ メトリクス集約 (JSONL → SQLite)
        ├─ レポート生成 (HTML / Markdown)
        └─ 通知 (Slack Webhook)
```

### 主要コンポーネント

| コンポーネント | 実装 | 役割 |
|---|---|---|
| bench_runner.py | Python 3.11 | 実行全体を統制し、メトリクスを収集 |
| engines/ | llama.cpp, vLLM, Ollama | モデルを実際に推論させるエンジン |
| tasks/ | YAML定義 | 評価タスク(プロンプトと期待出力)の定義 |
| metrics/ | JSONL + SQLite | 計測結果の保存と履歴管理 |
| report/ | Jinja2 + Markdown | 日次・週次レポートの生成 |
| notify/ | Slack Webhook | 閾値超過・失敗時の通知 |

### 評価タスクの分類

タスクは以下の4カテゴリに分類し、それぞれ代表プロンプトを定義する。

- **tok_fill**: 長文の要約(入力長2000トークン級)。プリフィル性能を主に測定する。
- **code_gen**: 関数実装・コード補完。出力品質と生成速度を測定する。
- **chat**: 多ターン会話(8ターン)。ターンごとの応答遅延を測定する。
- **stress**: 最大コンテキスト長・最大バッチでの連続生成。安定性と電力を測定する。

## 手順

### 事前準備(初回のみ)

1. ベンチマーク専用ワークステーションを確保する(GPU: 24GB VRAM以上、RAM: 64GB以上、NVMe SSD 1TB以上)。
2. 推論エンジンとモデル重み(例: Llama-3系、Mistral系、Qwen系)をダウンロードし、チェックサムを検証する。
3. 評価タスク定義ファイル `tasks/*.yaml` をリポジトリに配置する。
4. 計測用エージェント(GPU温度・電力取得)を有効化し、cron を登録する。

### 夜間実行の手順(毎晩)

1. **22:00 スケジュール起動**: cronにより `bench_runner.py` を起動する。
2. **プリフライトチェック**:
   - GPUがアイドル状態であることを確認する(使用率5%未満)。
   - ディスク空きが50GB以上あることを確認する。
   - 開発者の対話セッション(残存プロセス)がないことを確認する。
   - 条件を満たさない場合は実行を中止し、理由を通知して終了する。
3. **エンジン起動**: 対象モデルごとに推論エンジンをサブプロセスとして起動し、ヘルスチェックエンドポイントで応答を確認する。
4. **ウォームアップ**: 1回目の測定はキャッシュ効果で数値がぶれるため、捨てる前提で1回実行する。
5. **測定実行**: 各タスクを3回反復し、中央値をそのタスクの代表値とする。温度が85℃を超えた場合は測定を中断し、クールダウン後に再開する。
6. **エンジン停止とクリーンアップ**: サブプロセスを確実に停止し、GPUメモリが解放されたことを確認する。リークが検知された場合は翌日のアラート対象とする。
7. **集約と保存**: JSONLをSQLiteへ取り込み、実行メタデータ(エンジンバージョン、GPU温度、OSカーネル)を併記する。
8. **レポート生成と通知**: 前日比・7日移動平均との差分を計算し、閾値超過項目があればSlackへ通知する。

### 実行コマンド例

単発実行(手動テスト):

```bash
# 全モデル・全タスクを実行し、結果を ./results/ に保存
python bench_runner.py \
  --config config/nightly.yaml \
  --models llama3-8b,qwen2-7b \
  --tasks tok_fill,code_gen \
  --repeat 3 \
  --output ./results/$(date +%F).jsonl
```

エンジン別実行(llama.cpp経由):

```bash
llama-server \
  -m ./models/llama3-8b-instruct-q4_k_m.gguf \
  --host 127.0.0.1 --port 8080 \
  -ngl 99 -c 8192 &
sleep 10
curl -s http://127.0.0.1:8080/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"llama3-8b","messages":[{"role":"user","content":"要約してください: ..."}],"max_tokens":512}'
```

cron 登録(毎晩22:00):

```bash
# crontab -e
0 22 * * * /usr/bin/python3 /opt/bench/bench_runner.py --config /opt/bench/config/nightly.yaml >> /var/log/bench/cron.log 2>&1
```

レポート生成:

```bash
python -m report.generate --db ./metrics/bench.sqlite --since 7d --out ./reports/weekly.md
```

### 定期運用

- 日次: 前日比のチェックと異常通知。
- 週次: 7日移動平均の傾向レポート、モデル更新判断のレビュー資料生成。
- 月次: ハードウェア環境(ドライバ、BIOS)の固定確認、タスクセットの見直し。

## 評価方法

### 評価指標の定義

各指標は「同一マシン・同一温度範囲・同一パラメータ」で測定された中央値を用いる。単位と測定方法は以下の通り統一する。

- **生成速度**: デコード段階の 1秒あたり出力トークン数(tok/s)。
- **初動遅延**: リクエスト送信から最初のトークンが返るまでの時間(秒)。
- **プリフィル速度**: 入力トークンを処理する速度(tok/s)。
- **ピークVRAM**: 推論中のGPUメモリ使用量の最大値(GB)。
- **電力**: 測定区間の平均消費電力(W)、および1タスクあたりエネルギー(J)。
- **品質スコア**: 期待出力との一致度(正規化ハッシュ一致 + 簡易LLM-as-a-judgeの0〜5点)。
- **安定性**: 連続実行時の失敗率(タイムアウト・クラッシュの割合)。

### 評価項目表

| 評価項目 | 指標 | 測定方法 | 目標値 | 閾値(警告/重大) | 備考 |
|---|---|---|---|---|---|
| デコード速度 | tok/s | 3回反復の中央値 | 40 tok/s 以上 | 30 / 20 | モデル別で基準値を個別設定 |
| 初動遅延 | 秒 | 10リクエストの中央値 | 1.0 秒以下 | 2.0 / 4.0 | 長文入力時は別枠で評価 |
| プリフィル速度 | tok/s | 2000トークン入力 | 800 tok/s 以上 | 600 / 400 | 要約タスクで測定 |
| ピークVRAM | GB | nvidia-smi 1秒間隔サンプリング | 22 GB 未満 | 23 / 24 | 超過時はOOMリスクとして警告 |
| 平均電力 | W | 計測エージェント経由 | 350 W 以下 | 400 / 450 | コスト換算してレポート表示 |
| 品質スコア | 0〜5点 | 一致度 + LLM判定 | 4.0 以上 | 3.5 / 3.0 | 判定モデルは固定版を使用 |
| 失敗率 | % | 100リクエスト中の失敗数 | 0.5% 未満 | 1% / 3% | クラッシュは即重大扱い |
| 連続安定性 | 時間 | stress タスク 60分 | 中断なし | 1回中断 / 2回以上 | 温度85℃で自動中断 |

### 比較・判定ルール

1. **前日比**: 主要指標が前日中央値から10%以上悪化した場合「警告」、20%以上で「重大」とし、重大は即通知する。
2. **バージョン比較**: エンジンまたはモデルのバージョンが変わった日は、変更前後で最低2夜分の測定を行い、t検定風の簡易有意差判定(差がノイズ帯域の2倍超)で回帰を判定する。
3. **温度補正**: GPU温度が基準(65〜75℃)から外れた夜の測定は「補正必要」フラグを立て、傾向計算から除外する。
4. **品質と速度のトレードオフ表示**: レポートでは品質スコアとデコード速度を散布図で並べ、モデル選定に使える形にする。

## リスクと対策

### リスク一覧と対策表

| リスク | 影響度 | 発生可能性 | 対策 |
|---|---|---|---|
| 開発者の夜間作業と衝突し、測定値が汚染される | 中 | 高 | プリフライトでGPU使用率と残存プロセスを検知し、衝突時は中止して翌日に再スケジュール |
| モデル重みのダウンロード失敗・破損 | 高 | 中 | SHA256チェックサム検証、失敗時はキャッシュ済み旧版で継続 |
| OOM(GPUメモリ不足)によるクラッシュ | 高 | 中 | モデル別の事前メモリ試算、ピークVRAMの事前シミュレーション実行、コンテキスト長の上限管理 |
| 温度上昇によるサーマルスロットリングで測定値が劣化して見える | 中 | 高 | 温度サンプリングと補正フラグ、85℃で自動中断・クールダウン |
| 夜間無人実行での暴走(無限ループ・ゾンビプロセス) | 高 | 中 | 全体タイムアウト(6時間)、サブプロセスのセッション管理、watchdogによる強制停止 |
| 測定結果の漂移(ハードウェア加齢・ドライバ更新) | 中 | 中 | 実行メタデータ(ドライバ版、カーネル版)を必ず記録し、変更日をレポートで明示 |
| 電力コストの増大 | 中 | 中 | 1夜あたり実行予算(例: 最大6時間)を設定し、超過時はタスクを削減して実行 |
| 通知のアラート疲れ(誤検知の多発) | 低 | 高 | 閾値の段階化(警告/重大)、7日移動平均との比較によるノイズ低減 |
| 結果DBの肥大化 | 低 | 中 | 生JSONLは30日でアーカイブ、集約値のみSQLiteに保持 |
| 評価プロンプトへの過学習(タスクに合わせた不当な最適化) | 中 | 低 | タスクセットを四半期ごとに更新し、非公開ホールドアウトタスクを10%用意する |

### フェイルセーフ設計

- どの段階で失敗しても、必ず「実行した/しなかった」の記録が残り、翌朝のレビューで原因を追えるようにする。
- 推論エンジンの起動失敗はモデル単位でスキップし、他のモデルの測定は継続する(全体中止にしない)。
- 計測エージェントの異常は測定を続行しつつ「メトリクス欠損」として明示する(数値の信頼性を担保するため)。

## まとめ

本設計書は、日中の開発活動と干渉せずにローカルLLMの性能を継続的・再現性高く計測するための夜間ベンチマークシステムの全体像を示した。スケジューラから実行、計測、レポート、通知までの一気通貫の構成を定義し、評価指標として速度・遅延・メモリ・電力・品質・安定性の6系統を統一条件で測定する方法を定めた。評価項目表により目標値と警告/重大の閾値を明確化し、回帰の早期検出とモデル選定の判断基準を提供する。

リスク面では、夜間無人実行特有の問題(プロセス衝突、OOM、熱対策、暴走)に対してプリフライトチェック、温度補正、watchdog、実行予算といった具体的な対策を盛り込んだ。今後は、クラウドAPIとの比較、複数ノードでの並列測定、品質評価の拡充(非公開ホールドアウトタスクの本格運用)を拡張候補として段階的に取り込む。

まずは単一ワークステーション・3モデル・4タスクカテゴリで最小構成を開始し、2週間の試行運転を経て閾値とレポート内容を調整する。試行運転の結果を踏まえ、本設計書はv1.1として更新する予定である。
