# ローカルLLMの夜間ベンチマーク 設計書

## 目的

本プロジェクトの目的は、社内サーバーで稼働させているローカルLLM(大規模言語モデル)の性能を、夜間の未使用時間帯を利用して継続的に計測し、その結果を蓄積・比較可能な形で可視化することである。

日中帯は開発・検証用の推論リソースとして多忙であり、ベンチマーク実行に必要なGPUリソースを十分に確保できない。一方、夜間はGPUがほぼアイドル状態になるため、この遊休リソースを活用して定常的なベンチマークジョブを実行する。これにより、以下の目標を達成する。

- モデルの更新やドライバ・ランタイムのバージョンアップが推論性能に与える影響を、事前に定量的に把握する。
- レイテンシ(初-tokenまでの時間、token生成速度)やスループットの劣化を早期に検知する。
- 夜間バッチとしての運用を前提に、リソース競合や障害への耐性を設計に組み込む。
- 長期的なトレンド分析により、ハードウェアの増設やモデル選定の判断材料を提供する。

## 構成

本システムは以下の要素で構成される。

### 1. 対象モデル層

- 推論対象のローカルLLM(例: 7B〜70Bパラメータ規模のモデル)
- モデルチェックポイントのバージョン管理(Git LFS もしくはハッシュによる管理)

### 2. 推論エンジン層

- vLLM および llama.cpp を推論エンジンとして採用する。vLLMはバッチ推論のスループット測定に、llama.cppはCPU/GPU混在環境での従来構成との比較に使用する。
- CUDA および CUDA ドライバのバージョンを記録し、環境差分が結果に影響したかどうかを判別できるようにする。

### 3. ベンチマーク実行層

- ベンチマークツールは各エンジンの標準ベンチマーカー(`vllm bench serve`、`llama-bench`)を主とし、独自スクリプトで結果の整形を行う。
- 実行スケジューラとしてcronを採用し、每晚間23時(JST)にジョブを起動する。

### 4. 結果保存・可視化層

- 計測結果はJSON Lines形式で `results/` ディレクトリに日付付きファイル名で保存する。
- 可視化はGrafana + Prometheus(または簡易的にPython + Plotlyによる静的ダッシュボード)で行い、時系列トレンドを閲覧できるようにする。

## 手順

夜間ベンチマークは以下の手順で実行される。

1. 23:00 にcronがランナースクリプトを起動する。
2. ランナーはGPU使用率とメモリ空き容量を確認し、閾値未満(アイドル状態)であることを確認する。アイドルでない場合は実行をスキップし、その旨をログに残す。
3. 対象モデルをメモリにロードし、ウォームアップ用の推論を10リクエスト実行する。ウォームアップの結果は計測に含めない。
4. 本計測として、固定プロンプト集(後述の評価項目)に対して推論を実行する。各タスクは同一条件(温度0、同一シード、同一バッチサイズ)で実行し、再現性を担保する。
5. 結果をJSON Linesで保存し、前回・前々回の結果と比較して閾値超過の劣化があればSlack/メールで通知する。
6. 完了後、結果をPrometheusにpushし、ダッシュボードを更新する。

なお、同一環境での測定誤差を減らすため、計測中に他プロセスがGPUを占有しないよう、実行中にGPUロックファイルを取得する仕組みを持つ。

### 実行コマンドの例

```bash
# vLLM サーバを起動し、ベンチマーク対象として待受状態にする
vllm serve meta-llama/Llama-3.1-8B-Instruct \
  --max-model-len 8192 \
  --gpu-memory-utilization 0.90 \
  --port 8000
```

```bash
# サーバ起動後にスループットベンチを実行し、結果をJSONで保存
vllm bench serve \
  --model meta-llama/Llama-3.1-8B-Instruct \
  --base-url http://localhost:8000 \
  --num-prompts 200 \
  --save-result \
  --result-filename results/$(date +%Y%m%d).json
```

```bash
# llama.cpp 系の環境でのCPU/GPUハイブリッド計測例
llama-bench -m models/llama3-8b-q4_k.gguf -ngl 99 -p 512 -o results/llama-bench-$(date +%Y%m%d).json
```

## 評価方法

評価は以下の指標と項目で行う。すべての指標は同一ハードウェア・同一ソフトウェアバージョンを前提に、複数回(最低5回)実行した中央値を記録する。外れ値対策として最大値・最小値を除外した中央値を採用する。

| 評価項目 | 指標 | 測定条件 | 目標値(参考: 8Bモデル / A100 40GB) |
| --- | --- | --- | --- |
| 初-tokenレイテンシ(TTFT) | ms | 入力512トークン、バッチ1 | 300ms 以下 |
| スループット | tokens/sec | 連続200リクエスト、バッチ8 | 800 tokens/sec 以上 |
| メモリ使用量 | GiB | モデルロード直後とピーク時 | 36 GiB 以下 |
| 生成品質(回帰テスト) | 正答率(%) | MMLUサブセット100問 | 前回比 ±1% 以内 |
| 長時間安定性 | エラー率(%) | 8時間連続稼働 | 0.1% 未満 |
| 実行時間 | 分 | ベンチマーク全体 | 45分以内 |

評価は日次で自動実行し、週次で集計レポートを生成する。前回比で5%以上の性能劣化が発生した場合はアラート発報対象とする。

## リスクと対策

| リスク | 内容 | 対策 |
| --- | --- | --- |
| 熱・電力の影響 | 深夜の室温変化や電力制御が性能に影響し、トレンド分析を歪める | 室温・GPU温度を併記し、相関を分析する。異常値はメタデータで除外する |
| デイリーの環境変更 | デライバやライブラリの更新で結果が飛び、誤検知の原因となる | バージョン情報をメタデータとして保存し、バージョン変更時はベースラインを再構築する |
| 夜間バッチとの競合 | 他バッチとGPUを共有した場合にスループットが低下する | GPUロック機構と実行前チェックで競合を回避する |
| 測定ノイズ | 初回ロードやOSのスケジューリングゆらぎが誤差を生む | ウォームアップと複数回実行・中央値採用で吸収する |
| 結果ファイルの肥大 | 日次蓄積でストレージが圧迫される | 週次で集約・圧縮し、生データは30日でローテートする |

## まとめ

本設計では、夜間の遊休GPUリソースを活用してローカルLLMの性能を継続計測する仕組みを定義した。cronによる定時実行、固定条件での反復測定、結果の中央値採用とバージョン管理により、測定ノイズを抑えつつ長期的なトレンドを把握できる構成とした。本仕組みにより、環境変更やモデル更新が性能に与える影響を早期に検知し、安定した推論基盤の運用に貢献することを目標とする。
