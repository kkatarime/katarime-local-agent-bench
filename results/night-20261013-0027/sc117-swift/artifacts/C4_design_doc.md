# ローカルLLMの夜間ベンチマーク 設計書

- 文書バージョン: 1.0.0
- ステータス: 草案(レビュー待ち)
- 最終更新日: 2025-06-12
- 対象読者: 基盤基線チーム、ML基盤チーム、QAチーム

## 目的

本設計書は、開発マシンおよび社内GPUノード上で稼働するローカルLLM(以下「ローカルLLM」)の性能・安定性を、夜間の未利用時間帯を使って継続的に計測するための仕組み(以下「夜間ベンチマーク」)の設計を定義する。

背景として、日中時間帯は開発・検証用の推論リソースがほぼ常時稼働しており、ベンチマーク実行に必要な「他負荷が存在しない安定した測定環境」を確保できない。一方、夜間(22:00〜翌朝07:00)はGPUノードの稼働率が平均5%未満まで低下するため、同一条件での反復測定が現実的になる。この時間帯を活用し、以下を目的としてベンチマークを自動化する。

1. **性能劣化の早期検知**: モデル更新、推論エンジン(推論基盤)のバージョンアップ、ドライバやCUDAランタイムの更新が、スループットおよびレイテンシに与える影響を、リリース直後ではなく計画的に定量化する。
2. **ベースラインの確立と維持**: ハードウェア更新やモデル大型化に伴う性能変化を、単なる「体感」ではなく数値の系列として記録し、比較可能なベースラインを維持する。
3. **回帰テストとしての機能**: 推論パラメータ(スレッド数、コンテキスト長、量子化方式)などの設定変更が、意図しない性能退行を招いていないかを自動で検出し、翌朝のレビューで担当者が確認できる状態にする。
4. **容量計画への寄与**: 夜間バッチの所要時間実測値を基に、翌四半期のGPU容量・電力コスト・CO2換算排出量の予測モデルへ入力を提供する。

本活動は「開発中の実験」ではなく、**継続運用される計測基盤**として設計する。したがって、一度だけ実行して数値を記録する設計ではなく、毎晩同じ条件で実行され、同じ形式で結果が蓄積され、閾値逸脱時に通知されることを前提とする。

### 対象範囲(スコープ)

- 対象モデル: 社内配布対象のローカルLLM(量子化版を含む全バリアント)。
- 対象ハードウェア: 開発マシン(単一GPU)、社内GPUノード(2〜8 GPU)。
- 対象ワークロード: 単発推論(インタラクティブ用途)およびバッチ推論(夜間バッチ用途)の両方。

### 対象外(アウトオブスコープ)

- 生成品質(回答の正しさ)の評価。品質評価は別途「モデル評価パイプライン」で扱う。
- 分散推論(マルチノード)の性能測定。当面は単一ノード内のみを対象とする。
- 電力計測を伴わないハードウェアの故障検知。

## 構成

夜間ベンチマークは、以下の5つの要素で構成する。

### 1. 制御層(スケジューラ)

夜間の開始時刻にジョブを開始し、朝の時点で完了報告を出力する。実行は cron もしくは systemd timer を用いる。実行前には「前日の実行が正常終了したか」「GPUが他ジョブで占有されていないか」を確認し、条件を満たさない場合は実行をスキップして理由をログに残す。スキップも正常な状態であり、無断実行より記録されたスキップを優先する。

### 2. 計測層(ハーネス)

各モデル・各設定の組み合わせを、定義済みの実行計画(マトリクス)に従って逐次実行する。実行計画は YAML で管理し、実行対象・GPU種別・バッチサイズ・コンテキスト長・シード値を宣言的に記述する。ハーネスは各測定の開始・終了時刻をミリ秒精度で記録し、外乱(他プロセスによる割り込み)を検出した場合は当該測定の結果にフラグを付与する。

### 3. 測定対象(被測定系)

推論基盤はベンチマーク実行用に、日中とは分離した設定ファイルを用いる。これにより、日中の設定変更が夜間の測定値を意図せず変動させることを防ぐ。GPUノード側では、ベンチマーク時間帯に他ジョブの投入を停止する運用(運用側との合意事項)を前提とする。

### 4. データ層(結果ストア)

測定結果は1測定1レコードとして JSON Lines 形式で追記し、日次で集約して時系列データベースに格納する。レコードには最低限、実行日時、モデル識別子、ハードウェア識別子、実行計画のバージョン、全生指標、および実行環境のスナップショット(GPU温度、メモリ使用量、他プロセス数)を含める。

### 5. 報告層(レポートと通知)

毎朝08:00までに前夜の集約結果を生成し、閾値を逸脱した項目がある場合はチームチャネルへ通知する。閾値は「前回比」ではなく「過去7日移動平均比」で判定し、単晩のノイズによる誤通知を抑える。

## 手順

### 事前準備(初回のみ)

1. 対象GPUノードにベンチマーク用アカウントを作成し、日中ジョブとのリソース分離を確認する。
2. 実行計画(YAML)をリポジトリへ登録し、レビューを受ける。
3. 測定ハーネスの依存関係をロックファイルで固定し、実行環境を再現可能にする。
4. 初回実行を「ベースライン実行」として位置づけ、結果を凍結して以後の比較基準とする。

### 毎晩の実行手順

1. **22:00 起動チェック** — GPU稼働率、温度、ディスク空き容量を確認し、閾値内でなければスキップ判定。
2. **22:10 環境スナップショット取得** — GPU温度、メモリ使用量、稼働プロセス一覧を記録。
3. **22:15 計測開始** — 実行計画に従い、各測定をシード固定で最低5回反復。順序は固定とし、実行順の影響を排除するため順序は四半期ごとに見直し、見直し時はベースラインを再取得する。
4. **05:30 計測終了** — 全測定が完了しない場合は、完了分までを記録し、未完分を「時間不足」として記録。
5. **06:00 結果の整形と追記** — 生ログをJSON Linesへ変換し、外乱フラグを付与。
6. **07:30 集約とレポート生成** — 過去7日移動平均との比較、閾値判定、グラフ生成。
7. **08:00 通知送信** — 逸脱ありの場合はチャネルへ、なしの場合は日次サマリのみ。

### 変更管理手順

実行計画の変更は必ずプルリクエスト経由とし、変更後の初回実行は「ベースライン再取得」を伴うものとして、以後7日間の比較対象を旧ベースラインに固定する。

## 評価方法

評価は「性能」「安定性」「効率」の3軸で行う。各指標は5回反復の中央値を用い、外乱フラグ付き測定は集計から除外する。

### 評価項目と判定基準

| 評価項目 | 指標 | 測定条件 | 判定基準(閾値) | 判定方法 |
|---|---|---|---|---|
| 単発推論レイテンシ(初出字まで) | TTFT [ms] | コンテキスト4k、バッチ1 | 過去7日移動平均比 +10%超で警告、+20%超で異常 | 自動判定 |
| 単発推論スループット | 出力トークン/秒 | 入力512、出力1024、バッチ1 | 過去7日移動平均比 -10%超で警告 | 自動判定 |
| バッチ推論スループット | 出力トークン/秒 | バッチ32、コンテキスト8k | 過去7日移動平均比 -5%超で警告 | 自動判定 |
| 推論安定性(分散) | レイテンシの変動係数 [%] | 同一条件5回反復 | 変動係数 8%超で異常 | 自動判定 |
| メモリ使用効率 | ピークVRAM使用量 [MiB] | 全測定共通 | 実行計画で定義した上限超過で異常 | 自動判定 |
| 電力あたり効率 | トークン/ジュール | バッチ32測定時 | 過去7日移動平均比 -15%超で警告 | 手動レビュー併用 |
| 長期安定性(ドリフト) | 30日移動平均の傾向 [%] | 全項目 | 単調に5%以上悪化した場合 | 月次レビュー |

### 判定とエスカレーション

- **警告**: 翌朝のレビューで担当者が原因候補を確認し、2営業日以内に調査結果を記録。
- **異常**: 直ちに調査を開始し、原因が特定できるまで実行計画の変更を凍結。リリース済み変更が原因の場合は、該当変更の責任者へエスカレーション。
- **ドリフト**: 月次レビューで容量計画へ反映。

### 統計手法

反復回数が少ないため、平均値ではなく中央値を用いる。閾値判定は移動平均比で行い、単晩の異常値による誤判定を避ける。外乱フラグ付きデータは集計から除外するが、除外率が20%を超えた場合は計測環境自体を疑い、運用側へ確認する。

## 実行コマンド例

```bash
# 夜間ベンチマーク全体を、指定した実行計画に従って実行する
bench harness run --plan plans/nightly_v3.yaml --seed 42 --repeat 5 \
  --output results/$(date +%F).jsonl --snapshot-env
```

```bash
# 単一項目だけを素早く確認する場合(デバッグ用、結果は本系列に含めない)
bench harness run --plan plans/nightly_v3.yaml --only ttft_4k_b1 --seed 42 --dry-run-report
```

```bash
# 前夜の結果を集約し、閾値判定とレポート生成を行う
bench report aggregate --window 7d --input results/ --output reports/$(date +%F).md --notify
```

## リスクと対策

| リスク | 影響 | 発生可能性 | 対策 |
|---|---|---|---|
| 夜間に他ジョブが割り込み、測定値が乱れる | 誤検知・再実行コスト | 高 | 運用側との時間帯合意、外乱フラグによる自動除外、割り込み検知のログ強化 |
| GPU温度上昇による性能低下(夏期) | 季節的なドリフトと実劣化の混同 | 中 | 環境スナップショットを必須化し、温度補正係数を移動平均に反映 |
| 実行計画変更によるベースライン分断 | 過去系列との比較不能 | 中 | 変更は必ずベースライン再取得とセット、変更履歴をYAMLに記録 |
| 計測ハーネス自体のバージョン変更 | 測定方法の変更が性能変化と混同される | 中 | ハーネス変更も実行計画バージョンへ反映、変更時は旧ハーネスとの並行計測を1週間実施 |
| 通知の誤検知による警告疲労 | 異常が見逃される | 中 | 移動平均比判定、閾値の四半期見直し、警告と異常の通知経路分離 |
| 朝の運用開始までに集約が間に合わない | 担当者が朝のレビューで結果を確認できない | 低 | 07:30締切、集約処理の軽量化、遅延時は前夜の生ログをそのまま提示 |
| 単晩の完走不可(時間不足) | 系列の欠測 | 低 | 実行計画の総所要時間を6時間以内に設計、欠測はスキップとして明示記録 |

## まとめ

本設計は、夜間の未利用リソースを活用してローカルLLMの性能を継続計測し、劣化を早期に検知するための基盤を定義した。要点は以下の3点である。

1. **同じ条件で毎晩実行されること**が設計の前提であり、実行計画・ハーネス・測定対象の分離により再現性を担保する。
2. 評価は性能・安定性・効率の3軸で行い、判定は中央値と過去7日移動平均比を用いて、単晩のノイズと実劣化を区別する。
3. 検知した異常は自動判定とエスカレーションにより、翌朝のレビューで担当者が行動を起こせる状態までを本設計の範囲とする。

今後は、マルチノード分散推論への拡張、電力計測の本格導入、および季節変動の補正モデル化を次フェーズの検討事項とする。レビューで合意が取れ次第、初回ベースライン実行へ移行する。
