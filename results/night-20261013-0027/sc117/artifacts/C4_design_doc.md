# ローカルLLMの夜間ベンチマーク 設計書

- 文書版数: v1.0
- ステータス: 設計（レビュー待ち）
- 最終更新: 2026-02-14

---

## 目的

### なぜ夜間に測るのか

ローカルLLM（自前マシンで動かす大規模言語モデル）の実行性能は、日中の業務負荷や人の操作、
バックアップジョブ、OSのアップデートなどの影響を大きく受けやすい。日中に短時間のベンチマークを
回しても、得られた数値は「たまたま空いていた時間帯の最良値」になりやすく、実運用の体感や
SLA の根拠としては使えない。

本プロジェクトの目的は、**夜間の静穏な時間帯に、同一条件・同一手順で反復可能なベンチマークを
自動実行し、ローカルLLMの実性能を時系列で蓄積すること**にある。具体的には次の4点を達成する。

1. **性能劣化の早期検出**: ハードウェアのサーマルスロットリング、GPUメモリリーの蓄積、
   ドライバ更新による性能変化を、日次トレンドから検知する。
2. **モデル/ランタイム比較の公平化**: 量子化方式（FP16 / INT8 / INT4）、推論エンジン
   （llama.cpp / vLLM / Ollama 等）、コンテキスト長の違いを、同一夜間条件で比較する。
3. **容量計画の定量化**: 実運用で必要なスループット（tokens/sec）を、混雑時間帯ではなく
   基準ラインとして把握し、マシン増設やモデル縮退の判断材料にする。
4. **回帰テストとしての回線**: 推論基盤の構成変更（OS更新、ライブラリ更新、BIOS設定変更）の
   直後に夜間ベンチを走らせ、性能の段差変化を自動で検出する。

### 非目的（スコープ外）

- 出力の質（回答の正確性・有害性）の評価は本設計の対象外とする。質の評価は別途
  評価用データセットを用いたオフライン評価で行う。
- クラウドAPI（リモート推論）との比較は対象外。ネットワーク往復が計測を汚すため、
  比較が必要になる場合は別文書で扱う。
- 電力コスト最適化そのものは目的ではなく、消費電力は観測項目の一つとして扱う。

## 構成

### 全体アーキテクチャ

夜間ベンチマークは、次の5コンポーネントで構成する。すべて単一のGPUワークステーション上で
完結させ、外部ネットワーク依存をゼロにする（ネットワーク遅延を測らないため、DNS解決や
プロキシ設定に左右されるHTTPクライアントは使わない）。

```
┌────────────────────────────────────────────────────────┐
│                    Scheduler (cron)                    │
│            平日 02:00 JST に nightly_run.sh を起動      │
└───────────────┬────────────────────────────────────────┘
                │
┌───────────────▼────────────────────────────────────────┐
│                 Runner (nightly_run.sh)                │
│  環境収集 → ワームアップ → 計測ループ → 結果整形        │
└───────────────┬────────────────────────────────────────┘
                │
   ┌────────────┼─────────────┬──────────────────┐
   ▼            ▼             ▼                  ▼
┌──────────┐ ┌──────────┐ ┌────────────┐ ┌──────────────┐
│ Inference│ │  Env     │ │  Metrics   │ │  Result      │
│ Engine   │ │  Probe   │ │  Collector │ │  Writer      │
│llama.cpp │ │ nvidia-smi││ telemetry  │ │ JSONL/CSV    │
│vLLM      │ │ sensors  ││  (CPU/GPU) │ │  + ハッシュ   │
└──────────┘ └──────────┘ └────────────┘ └──────────────┘
                │
┌───────────────▼────────────────────────────────────────┐
│           Analyzer (weekly_report.py)                  │
│   週次集計 / 外れ値検出 / 段差検出 / Markdownレポート   │
└───────────────┬────────────────────────────────────────┘
                │
┌───────────────▼────────────────────────────────────────┐
│           Notifier (Slack / メール / ローカルログ)      │
└────────────────────────────────────────────────────────┘
```

### 計測対象ハードウェアとソフトウェア

| 層 | 構成要素 | バージョン方針 |
|---|---|---|
| ハードウェア | NVIDIA RTX 4090 (24GB) × 1、CPU 16コア、RAM 64GB、NVMe 2TB | 夜間ベンチ実行中はBIOSの省電力設定を固定 |
| OS | Ubuntu 24.04 LTS | 夜間ベンチ時間帯は unattended-upgrades を停止 |
| ドライバ | NVIDIA Driver 550系 | 更新時は「更新前後で1夜ずつ」計測して段差を確認 |
| 推論基盤 | llama.cpp（主）、vLLM（副） | 実行時にコミットハッシュを記録し、結果レコードに埋め込む |
| モデル | 7B / 13B / 70B 量子化バリアント | 固定のモデル一覧（モデルレジストリ）から選択 |
| データ | 固定プロンプト集（後述） | 変更時はデータセットのSHA-256を更新 |

### ディレクトリ構成

```

│   └── collect_env.sh        # 環境メタデータの収集
├── configs/
│   ├── models.yaml           # 計測対象モデルの定義
│   ├── workloads.yaml        # ワークロード（プロンプト長・出力長）の定義

│   └── prompts/
│       ├── short_qa.jsonl    # 短い質問応答（入力128 / 出力256）
│       ├── long_ctx.jsonl    # 長文要約（入力8192 / 出力512）
│       └── code_gen.jsonl    # コード生成（入力512 / 出力1024）
├── results/
│   ├── raw/                  # 生JSONL（日付ごとに追記、上書き禁止）
│   ├── csv/                  # 集計用CSV

├── scripts/
│   ├── analyze.py            # トレンド・外れ値・段差検出
│   └── notify.py             # 閾値超過時の通知
└── docs/
    └── design.md             # 本書
```

### 結果レコードのスキーマ

1レコード = 1モデル × 1ワークロード × 1反復。JSON Lines で追記する。必須フィールドは次のとおり。

- `run_id`: 実行UUID（夜間実行1回ごとに1つ、全レコードで共有）
- `timestamp_utc`: 計測開始時刻（UTC、ISO 8601）
- `model`: モデル識別子（例 `llama3-8b-instruct-q4_k_m`）
- `engine`: 推論エンジン名とコミットハッシュ
- `workload`: ワークロード名と入出力トークン長
- `prompt_sha256`: 使用したプロンプト集のハッシュ
- `metrics`: 後述の「評価方法」で定義する指標のオブジェクト
- `env`: GPU温度、GPU使用率、CPU温度、メモリ使用量、GPUクロック、他
- `status`: `ok` / `warmup_skipped` / `failed` / `throttled`

## 手順

### 事前準備（初回のみ）

1. 計測対象マシンに推論基盤をインストールし、モデルファイルを検証済みで配置する。
2. `configs/models.yaml` に計測対象を登録する。各モデルについて、ファイルパス、量子化形式、
   期待されるVRAM使用量、コンテキスト長上限を記載する。
3. プロンプト集を作成し、SHA-256を記録する。プロンプトは**永久に固定**する。
   内容を変える場合は新しいファイル名にし、ハッシュを更新する（既存結果との比較可能性を守る）。
4. `thresholds.yaml` に閾値を設定する。初期値は、最初の2週間の計測で得られた
   中央値を基準ラインとし、基準比で -10% を警告、-20% を重大として設定する。
5. cron を登録する。

### 毎晩の実行手順

夜間実行は 02:00 JST 開始、所要時間 90分以内 を上限とする。手順は次の順序で、
**順序そのものが計測条件**であるため変更してはならない。

1. **排他制御**: `flock` により、同一マシン上の他ジョブ（バックアップ、学習ジョブ等）と
   排他する。ロックが取れなければ 15分待って再試行、それでも取れなければ
   `status=skipped` のレコードを書き、理由を記録して終了する。
2. **環境の静穏性チェック**: GPU使用率が過去5分間 5% 未満であること、GPU温度が
   55℃以下であることを確認する。条件を満たさなければ計測を中止し、理由を記録する。
   これは「計測できないことを計測する」ための設計である。
3. **環境メタデータの収集**: `collect_env.sh` を実行し、ドライバ版数、GPUクロック、
   CPU温度、メモリ空き、ディスク空き、OSアップデート履歴の要約を取得する。
4. **サーマルワームアップ**: 対象モデルを1回、計測対象ワークロードとは別の
   固定プロンプトで推論し、GPU温度とクロックを安定させる（1回目特有の
   JIT/キャッシュ効果を除く）。ワームアップ結果は評価に含めない。
5. **計測ループ**: `models.yaml` の登録順に、各モデル × 各ワークロードを
   3反復実行する。反復間は60秒のクールダウンを挟み、直前反復のGPU温度を記録する。
6. **メトリクス収集**: 推論中は1秒間隔で `nvidia-smi` と `/sys/class/hwmon` を読み、
   温度・消費電力・クロックの時系列をメトリクスに添付する。
7. **結果の書き出し**: 1レコードごとに `results/raw/YYYY-MM-DD.jsonl` に追記し、
   最後にファイル末尾に `run_id` の完了レコードを書く（途中でクラッシュした場合に
   不完全実行を識別できるようにするため）。
8. **後処理**: 一時ファイルを削除し、`results/raw/` を日次で外部ディスクにコピーする。
9. **閾値判定と通知**: `analyze.py --daily` を実行し、閾値超過があれば通知を送る。

### 週次手順

- 月曜 09:00 JST に `analyze.py --weekly` を cron で実行し、`results/reports/` に
  Markdownレポートを生成する。
- 人間はレポートを見て、外れ値の理由（ハードウェア起因 / ソフトウェア起因 / 計測起因）を
  トリアージし、`triage` ラベルをレコードに付与する。ラベル付与は追記のみで行い、
  生レコードを書き換えない。

### 実行コマンドの例

通常の日次実行（cron から呼ばれるのと同じ入口）:

```bash
#!/usr/bin/env bash
# bin/nightly_run.sh - 夜間ベンチマークの日次実行
set -euo pipefail

RUN_ID="$(uuidgen)"
DATE_UTC="$(date -u +%Y-%m-%d)"
RAW_DIR="results/raw"
LOCK="/tmp/nightly-bench.lock"

mkdir -p "${RAW_DIR}"

# 1) 排他制御: 他のGPUジョブと競合したら諦める
exec 200>"${LOCK}"
if ! flock -w 900 200; then
  echo "{\"run_id\":\"${RUN_ID}\",\"status\":\"skipped\",\"reason\":\"lock_timeout\"}" \
    >> "${RAW_DIR}/${DATE_UTC}.jsonl"
  exit 0
fi

# 2) 環境の静穏性チェック（GPU使用率 < 5% かつ温度 <= 55℃）
./bin/check_quiet.sh || {
  echo "{\"run_id\":\"${RUN_ID}\",\"status\":\"skipped\",\"reason\":\"not_quiet\"}" \
    >> "${RAW_DIR}/${DATE_UTC}.jsonl"
  exit 0
}

# 3) 環境メタデータ収集
ENV_JSON="$(./bin/collect_env.sh)"

# 4) ワームアップ（評価には含めない）
./bin/bench_once.sh --model llama3-8b-instruct-q4_k_m \
  --workload warmup --reps 1 --warmup-only

# 5) 本計測: 全モデル × 全ワークロード × 3反復
./bin/bench_all.sh \
  --config configs/models.yaml \
  --workloads configs/workloads.yaml \
  --reps 3 \
  --run-id "${RUN_ID}" \
  --env-json "${ENV_JSON}" \
  --out "${RAW_DIR}/${DATE_UTC}.jsonl"

# 6) 閾値判定と通知
python3 scripts/analyze.py --daily --date "${DATE_UTC}" \
  --thresholds configs/thresholds.yaml
```

単一モデル・単一ワークロードを手動で計測する例（デバッグ用）:

```bash
./bin/bench_once.sh \
  --model llama3-8b-instruct-q4_k_m \
  --engine llama.cpp \
  --workload long_ctx \
  --reps 3 \
  --prompt-file data/prompts/long_ctx.jsonl \
  --seed 42 \
  --temperature 0 \
  --metrics-out results/raw/manual_$(date +%Y%m%d_%H%M%S).jsonl
```

週次レポート生成と、特定日の結果をCSVに整形する例:

```bash
# 週次レポート（月曜 09:00 に cron 実行されるものと同じ）
python3 scripts/analyze.py --weekly \
  --since "$(date -u -d '7 days ago' +%Y-%m-%d)" \
  --report-out results/reports/weekly_$(date -u +%Y-%m-%d).md

# 特定日の生JSONLをCSVに整形（スプレッドシートでの確認用）
python3 scripts/analyze.py --to-csv \
  --input results/raw/2026-02-13.jsonl \
  --output results/csv/2026-02-13.csv
```

## 評価方法

### 指標の定義

すべての指標は「推論開始から完了まで」の実時間に基づき、トークン数はトークナイザで
実際にカウントした値を使う（推定値ではない）。`temperature=0`、`seed` 固定で決定性を担保する。

| 指標 | 定義 | 単位 | 算出方法 | 基準ライン | 警告閾値 | 重大閾値 |
|---|---|---|---|---|---|---|
| `decode_tps` | デコード速度（出力トークン/秒） | tokens/s | 出力トークン数 ÷ デコード実時間 | 直近14日中央値 | 基準比 -10% | 基準比 -20% |
| `prefill_tps` | プリフィル速度（入力トークン/秒） | tokens/s | 入力トークン数 ÷ プリフィル実時間 | 直近14日中央値 | 基準比 -10% | 基準比 -20% |
| `ttft_ms` | 最初のトークンまでの時間 | ms | 推論開始 → 1トークン目出力 | 直近14日中央値 | 基準比 +15% | 基準比 +30% |
| `e2e_ms` | 1リクエストの総応答時間 | ms | 推論開始 → 生成完了 | 直近14日中央値 | 基準比 +10% | 基準比 +20% |
| `vram_peak_mb` | ピークVRAM使用量 | MB | 計測中の `nvidia-smi` 最大値 | 期待値（モデル定義） | 期待値 +5% | 期待値 +10% |
| `power_avg_w` | 平均消費電力 | W | 1秒間隔サンプリングの平均 | 直近14日中央値 | 基準比 +15% | 基準比 +30% |
| `gpu_temp_max_c` | 最大GPU温度 | ℃ | 計測中の最大値 | 83℃（絶対値） | 85℃ | 90℃ |
| `throttle_ratio` | クロック低下区間の割合 | 0-1 | 基準クロック未満のサンプル数 ÷ 総サンプル数 | 0.05 | 0.10 | 0.20 |
| `repro_cv` | 3反復の `decode_tps` 変異係数 | 0-1 | 標準偏差 ÷ 平均 | 0.03 | 0.05 | 0.10 |

### ワークロード別の評価観点

ワークロードは指標の感度を変えるため、下表のように「どの指標を主として見るか」を決めておく。

| ワークロード | 入力/出力トークン | 主指標 | 副次指標 | 検出したい劣化 |
|---|---|---|---|---|
| `short_qa` | 128 / 256 | `ttft_ms` | `decode_tps` | モデルロード時間、KVキャッシュ確保、CPU側オーバーヘッド |
| `long_ctx` | 8192 / 512 | `prefill_tps` | `vram_peak_mb` | VRAM不足、アテンション実装の退化、メモリ帯域の低下 |
| `code_gen` | 512 / 1024 | `decode_tps` | `e2e_ms` | デコードパスの性能、量子化カーネルの退化 |

### 集計と外れ値の扱い

- 日次集計は、その日の反復値から `repro_cv` が閾値を超えるレコードを「信頼性不良」として
  分離し、主トレンドには含めない（分離したレコードは捨てず、原因調査の対象として保持する）。
- 週次集計は、日次中央値の系列に対して移動中央値 ± 3×MAD（中央値絶対偏差）で外れ値を検出する。
  平均を使わないのは、1回の異常値がトレンド全体を引っ張るのを避けるためである。
- 段差検出（レベルシフト）は、連続する7日中央値の系列に対し、前週比での変化量が重大閾値を
  超えた地点を検知点とする。検知点の日付と、その前後で変化した可能性のある構成要素
  （ドライバ版数、エンジンコミット、OS更新履歴）をレポートに併記する。

### 比較表の出力形式

週次レポートには、モデル間の比較を次の形式で掲載する。

| モデル | 平均 decode_tps | 前週比 | ttft_ms p95 | VRAMピーク | 状態 |
|---|---|---|---|---|---|
| llama3-8b-instruct-q4_k_m | 62.4 | -1.2% | 118 | 6,120 | 正常 |
| mistral-7b-instruct-q5_k_m | 68.1 | -0.4% | 104 | 5,480 | 正常 |
| llama3-70b-instruct-q4_k_m | 11.8 | -18.6% | 940 | 22,900 | 重大（要調査） |

## リスクと対策

### 計測の信頼性を損なう要因

| リスク | 影響 | 発生可能性 | 対策 |
|---|---|---|---|
| 夜間のOS自動アップデートが計測中に走る | 段差ではなくノイズとして現れ、トレンドを汚す | 高 | 02:00–03:30 は unattended-upgrades をマスク。更新実施日はベンチをスキップし、翌日を「更新後1日目」として明示ラベルする |
| 他ユーザー/ジョブのGPU使用 | スループットが低下し、原因切り分けが困難に | 中 | `flock` による排他、開始前の静穏性チェック、GPUプロセス一覧の記録 |
| サーマルスロットリング | 同一設定でも日によって速度が変わる | 中 | ワームアップで温度を安定化、`throttle_ratio` と `gpu_temp_max_c` を独立指標として記録し、スロットリング時のレコードはトレンドから分離 |
| 電源計画/省電力設定の変更 | 数%〜十数%の段差が「性能劣化」と誤認される | 中 | 開始時に電源計画値を収集し、前回実行と違えばレコードに `env_changed` フラグを付与。BIOS設定変更は変更申請プロセスで記録 |
| モデルファイルの破損・差し替え | 別モデルを測ってしまい、比較が無意味になる | 低 | 実行前にモデルファイルのSHA-256を検証。不一致なら `failed` で終了 |
| VRAM不足によるCPUオフロード | 見かけ上大幅な低速化。量子化変更と区別がつかない | 中 | `vram_peak_mb` とオフロード層数のログを記録。オフロード発生時は `status=throttled` とは別に `offload=true` を付与 |
| 決定性不足（サンプリング、並列順序） | 反復間の変動が増え、`repro_cv` が閾値超え | 中 | `temperature=0`、`seed` 固定、バッチサイズ固定。バッチサイズを変えた実験は別系列として扱う |
| 計測コード自体のバグ | 指標定義の変更が「性能向上/劣化」として現れる | 低 | 指標算出コードの版数をレコードに記録。定義変更時は新旧定義で並列計測する移行期間を設ける |

### 運用上のリスク

| リスク | 影響 | 対策 |
|---|---|---|
| 通知の誤検知が多すぎて無視される（アラート疲れ） | 重大な劣化も見逃す | 警告は日次でまとめて1通、重大のみ即時。閾値は四半期ごとに見直し、誤検知率をレポートで可視化 |
| 結果ファイルの肥大化 | ディスク逼迫、集計の遅延 | JSONLの日次ローテーション、1年分保持後にgzip圧縮、CSVは直近90日のみ生成 |
| 単一マシン依存（単一障害点） | マシン停止で系列が途切れ、トレンドが再構築できない | 停止レコード（`status=skipped`）を必ず残す。可能なら第2マシンで同一構成の系列を並行運用 |
| 夜間実行が学習ジョブと常時衝突する | ベンチが回らず、データが欠損する | 学習ジョブのスケジューラに「夜間ベンチ優先」の枠を予約させ、衝突時は学習側を遅延させる |
| 結果の手動編集による汚染 | 数値の信頼性が失われる | 生レコードは追記のみ。修正は `triage` ラベルの追記で行い、編集はPRレビュー必須とする |

### セーフティメカニズム

- 実行全体に 90分のタイムアウトを設け、超過時は完了分までを書き出して終了する。
- 1夜で失敗レコードが半数を超えた場合は、性能劣化ではなく計測系の異常として
  「計測系アラート」を別系統で発報する（性能アラートと混同しないため）。
- 通知チャネルが不通の場合に備え、通知内容自体は常にローカルログにも書く。

## まとめ

本設計は、ローカルLLMの実性能を「日中の一回の計測」ではなく「夜間の静穏条件下での
日次系列」として捉え直すことを中核に置いている。固定プロンプト・固定シード・固定順序と
いう厳格な条件、およびワームアップとクールダウンによる熱的条件の統制により、
計測値から環境ノイズを可能な限り除去する。同時に、`throttle_ratio` や `env_changed` のような
「計測条件そのもののメタデータ」を第一級のデータとして扱うことで、劣化がモデル由来なのか
環境由来なのかを切り分けられるようにした。

評価の中心は `decode_tps` / `prefill_tps` / `ttft_ms` の3指標であり、これらをVRAM使用量、
消費電力、GPU温度、反復再現性と組み合わせて多角的に判定する。閾値は絶対値ではなく
直近14日中央値に対する相対変化で定義し、マシン固有の絶対性能の違いに依存しない
運用を可能にしている。外れ値と段差の検出には平均ではなく中央値ベースの統計を使い、
稀な異常値がトレンドを壊さない設計にした。

次のステップは次のとおりとする。

1. `bin/` 配下のスクリプトプロトタイプの実装と、2週間の並走計測（閾値の初期化）。
2. 第2マシンでの系列並行化の要否判断（学習ジョブとの競合頻度を見て決定）。
3. 質の評価（オフライン評価）との統合。夜間ベンチで性能が正常な夜にのみ質評価を走らせる、
   という依存関係の設計を別文書で行う。

本設計の前提として、性能の数値は「その夜にその条件で測った値」でしかないことを
常に意識する。系列の価値は単一の数値ではなく、条件の記録とセットで保存された
連続性から生まれる。この原則を崩す変更（プロンプト変更、指標定義変更、ワークロード追加）は、
必ず新旧並列計測を経ることとする。
